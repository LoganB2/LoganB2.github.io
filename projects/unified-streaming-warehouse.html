Unified Streaming Data Warehouse

Collapsed 20+ per-client streaming model outputs into one standardized, self-discovering table so every downstream report reads from a single source of truth instead of stitching together dozens of inconsistent ones.

Databricks PySpark Delta Lake Data Engineering

01 Problem

Each client's streaming ad-performance model wrote its output to its own table, with its own column layout, metric definitions, and quirks. More than twenty of these tables existed, and every downstream report — dashboards, summaries, audits — had to hand-write logic to read from whichever subset of clients it covered. Adding a client meant touching every consumer separately, and there was no single place to answer a cross-client question.

02 Approach

  • Built auto-discovery logic that finds each client's model output table by naming convention, with a small hand-maintained override list for the rare client whose data lives somewhere non-standard.
  • Gated every client on having a minimum amount of trailing data before being included, so partial or newly onboarded clients don't corrupt cross-client aggregates.
  • Designed a shared schema — a fixed set of common dimensions plus a small number of flexible, named metric slots — that every client's table gets projected onto, since metric definitions vary client to client.
  • Unioned every client onto that schema into one large table, partitioned by broadcast week for query performance, refreshed twice daily inside Databricks.

03 Technical Highlights

  • Schema harmonization via flexible slots — rather than forcing every client's metrics into identical named columns (which would break as soon as a client's model changed), the schema exposes a handful of generically named metric slots whose meaning is documented per client. This let heterogeneous models coexist in one table without constant migrations.
  • Auto-discovery over hardcoding — new clients are picked up automatically as soon as their model table exists and clears the data-sufficiency gate, cutting onboarding from a manual integration step to a no-op in the common case.
  • Caught a write-path footgun before it shipped — the table's existing "incremental write" flag looked safe to enable for performance, but tracing the write path showed flipping it as-is would silently wipe historical data instead of appending to it. Flagged and left disabled pending a real incremental-write redesign, rather than risk history loss for a performance win.

04 Outcome

One table — billions of rows across dozens of advertisers — now serves as the single source of truth for cross-client streaming reporting, replacing what had been a per-client patchwork. New clients onboard automatically instead of requiring a manual integration pass, and a silent data-loss bug was caught and headed off before it ever ran in production.
