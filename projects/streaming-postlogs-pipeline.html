Streaming Postlogs Pipeline

A daily pipeline that standardizes streaming (CTV/OTT) ad impression logs from several vendors into a consistent format, feeding dozens of live dashboards — and the fix for a partition bug that had been quietly corrupting monthly totals.

Databricks PySpark SQL Data Engineering

01 Problem

Streaming ad impression data arrived from several different vendors, each with its own log format, granularity, and quirks — some impression-level, some pre-aggregated. Dashboards needed one consistent view across all of them. On top of that, an existing bug meant that whenever the job's write logic ran at the wrong time grain, it could silently overwrite a full month of totals with partial data — and nothing would flag it as wrong.

02 Approach

  • Built a daily standardization job that reads each vendor's feed — including both raw impression-level logs and pre-aggregated vendor summaries — and writes them into a common table structure.
  • Root-caused the partition bug: the write path replaced data at whatever time grain the current read happened to use, so a weekly read could overwrite (and effectively truncate) a monthly partition. Fixed the rule so reads always match the grain of the partition being replaced.
  • Built household frequency logic that blends viewing-behavior factors for linear-style vs. streaming inventory, weighted by each campaign's share of streaming spend, to produce a more accurate frequency estimate than either factor alone.
  • Kept downstream-facing column names stable on purpose, even where they're unconventional, because dozens of live dashboards depend on exact column names and a rename would break them silently.

03 Technical Highlights

  • Partition-grain discipline — traced a subtle bug back to a mismatch between the grain of an incoming read and the grain of the partition it was replacing, which had been silently freezing monthly totals at a fraction of their true value. The fix was a small rule change, but finding it required understanding the full write path, not just the symptom.
  • Weighted frequency blending — rather than picking one viewers-per-household factor for all inventory, blends a linear-style and an OTT-style factor in proportion to each campaign's actual streaming mix.
  • Backward-compatible schema decisions — chose to preserve existing, imperfect column naming rather than "clean it up," because the downstream BI layer resolves dashboard cards by exact column name and a rename would have broken dozens of them with no warning.

04 Outcome

The pipeline runs daily in production, feeding dozens of live dashboards with standardized, cross-vendor streaming data. The partition-grain fix corrected a data-quality issue that had been affecting monthly reporting, and the new frequency logic gave a more accurate household-reach estimate across linear and streaming inventory.
