Plain-English Campaign Data Chatbot

An internal tool that lets non-technical staff ask plain-English questions about ad campaign spend, impressions, and airings, and get back a trustworthy number, table, or chart — backed by an automated benchmark to keep it honest.

LLM Tool Use Python Streamlit Evaluation

01 Problem

Only people comfortable writing SQL could answer questions against the company's linear TV and streaming ad datasets — even simple ones like "how much did we spend on this campaign last week." Everyone else had to route the question to an analyst. A natural-language interface needed to be accurate enough to trust, safe enough to expose broadly, and honest about what it didn't know.

02 Approach

  • Built an LLM tool-use loop that writes SQL against the target datasets, tests it, and self-repairs once on a failed query before giving up gracefully.
  • Encoded dataset knowledge — routing rules, scope boundaries, and known traps like unit mismatches between datasets — directly into structured dataset specs that serve as the system prompt, rather than relying on the model to infer them.
  • Added guardrails: SELECT-only SQL, explicit decline behavior for out-of-scope questions (like performance questions the data can't answer), and full logging of every question asked.
  • Shipped a Streamlit UI on top and deployed it as an internal Databricks App so it's available without any local setup.
  • Built a benchmark harness that generates roughly 2,000 test questions, scores the bot's answers, and triages failures into "bot bug" vs. "test itself was wrong" — then extracted it into a portable package so another team could benchmark their own chatbot the same way.

03 Technical Highlights

  • Dataset specs as the system prompt — instead of hoping the model infers dataset quirks from examples, the specs directly document routing logic, scope limits, and unit traps (e.g., one dataset's counts being in thousands while another's are 1:1), making the model's behavior easier to reason about and fix.
  • Self-repair with a hard stop — the bot gets exactly one retry on a failed query before declining, balancing resilience against runaway retries or silently wrong answers.
  • Benchmark as a reusable package — the ~2,000-question harness and failure-triage logic were pulled out of the project-specific code into a standalone package specifically so a different team's chatbot could be scored with the same methodology.
  • Architecture tuned for cost vs. accuracy — model and pipeline choices were made deliberately to balance response latency and API cost against answer accuracy for a tool meant to run at broad internal scale.

04 Outcome

Deployed and in active use internally, scoring in the mid-80s percent on the full benchmark — materially higher once test cases with incorrect expected answers are excluded. The benchmark package is now being reused to evaluate a second, unrelated chatbot built by another team.
